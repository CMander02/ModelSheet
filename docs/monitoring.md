# Native ModelSheet monitoring

ModelSheet owns the monitoring configuration, source-aware scanner, observation
history, review queue and service lifecycle. Linux background execution uses
user systemd units generated by the CLI. No separate server monitoring script
is required. Run commands from the project checkout using `uv run modelsheet`.

## Start and operate

```bash
uv run modelsheet monitor init
uv run modelsheet monitor list
uv run modelsheet monitor run
uv run modelsheet monitor start
uv run modelsheet monitor status
uv run modelsheet monitor tasks --group zhipu
uv run modelsheet monitor tasks --events
uv run modelsheet monitor history
uv run modelsheet monitor logs
uv run modelsheet monitor stop
```

`run` scans immediately and exits. `start` installs/enables the persistent timer;
it does not promise an immediate scan. `stop` disables the timer and stops any
scheduled scan. A manually started foreground `run` is stopped through its
terminal. `status` reports schedule, service state and the latest scan result.
`tasks` is the catalog review queue; candidates remain pending until a subsequent
scan matches them to the reviewed catalog. It does not download weights or publish
models. Use `--json`, `--group` and `--limit` for structured task inspection.

The default daily schedule is 06:00 Asia/Shanghai:

```bash
uv run modelsheet monitor schedule --at 06:00 --timezone Asia/Shanghai
```

Changing a schedule reloads installed units and preserves whether the timer is
enabled. On systems without systemd, run `monitor run` from an external scheduler.
Background operation after logout requires the host's user manager to remain
available, usually through administrator-configured user lingering.

## One runtime source list

The default monitoring home is `.modelsheet/monitor/`, relative to this project.
Set `MODELSHEET_MONITOR_HOME` to an absolute path to use another location. The
generated service stores this path explicitly. One service pair is supported per
Unix user: `modelsheet-monitor.service` and `modelsheet-monitor.timer`.

- `config.json`: actual source groups, account aliases and schedule.
- `state/monitor-state.json`: persistent source observations and version baselines.
- `reports/latest.json`: full result, source commit/dirty status, grouped models and tasks.
- `reports/review-summary.md`: readable review counts, changes, failures and duplicates.
- `reports/monitored-organizations.md`: full configured source inventory at the latest run.
- `reports/20*.json`: completed reports, retained for 30 days.

`monitor list` reads current configuration immediately; generated reports describe
the configuration used by their last scan. Configuration/state writes and scans
share an exclusive process lock. Concurrent writers are rejected, preserving the
previous complete files. Runtime data is ignored by Git. The example in
`data/monitoring.example.json` is used only during initialization.

```bash
uv run modelsheet monitor add qwen --hf Qwen --ms Qwen --name Qwen
uv run modelsheet monitor add minimax --hf MiniMaxAI --ms MiniMax
uv run modelsheet monitor add zhipu --hf zai-org --ms ZhipuAI --name '智谱 / GLM'
uv run modelsheet monitor remove qwen --source hf
uv run modelsheet monitor check
```

Add/update sources using a stable group ID. Updating an account preserves its old
name as an identity alias. Removing a source stops polling while retaining its
aliases and historical observations. For a new publisher, verify official account
ownership before adding it. Different HF and MS account names belong in one group.
Advanced explicit model aliases and source preferences can be edited in `config.json`
while no scan is running, then checked with `monitor check`.

Once initialized, `modelsheet watchlist add/remove/list/search` uses this runtime
configuration. Known publishers retain their correct per-platform account names.
`watchlist search` runs the native persistent HF/MS monitor. Before initialization,
the legacy behavior remains available. `scan --watchlist` also reads the native
source list, while preserving the original one-shot scanner's options and snapshot
semantics. For persistent version tracking and full source-aware reporting, use
`monitor run`. `data/watchlist.json` is only the legacy fallback when native
monitoring has not been initialized. Provider metadata remains in `data/providers.json`.

## Identity and failure handling

A model has a stable group/model key and multiple source records, each with its
ID, URL, revision, update time and observation history. Explicit publisher aliases
and verified model aliases merge cross-platform or renamed repositories. Different
model-name variants are preserved. Existing ModelSheet filters still exclude
non-target repositories; remaining candidates require review.

Both platforms are paginated. API errors, malformed/empty known accounts,
incomplete pages or page-limit exhaustion fail that source without replacing its
baseline. A repository must be absent from two complete successful scans before it
is marked unlisted. Successful sources continue to update when another source fails;
the overall scan exits with status 2 and records a partial report.

ModelScope requests use the canonical endpoint and revalidate page responses.
An incomplete listing is retried once from page one with a fresh collection;
partial attempts are never combined into a complete baseline.

The first scan of an added source builds a baseline. Later scans distinguish newly
discovered models, new sources, repository updates and listing changes. An added
source does not cause old repositories to be announced as new releases. Repository
versions/timestamps can change because of documentation or configuration updates;
they do not establish weight changes or inference availability. No external
notification delivery is configured by these commands.

## Migrate a server installation

Stop the previous scheduler and ensure its current scan has finished. Back up its
configuration, state, reports and units. Then import the same schema-v2 files:

```bash
uv run modelsheet monitor init --from /path/to/monitoring.json \
  --state-from /path/to/monitor-state.json --reports-from /path/to/reports
uv run modelsheet monitor check
uv run modelsheet monitor run
uv run modelsheet monitor start
```

Initialization refuses to replace an existing configuration. Migration preserves
all source baselines and reports. Disable the previous scheduler after verification
so only one scheduler remains enabled. Old paths may be symlinked to the native
files for compatibility; they must not become a second writable configuration.

## Source updates and development

The scheduled service runs `monitor update --skip-dirty`, then `monitor run --build-db`.
Updating fast-forwards a clean Git checkout and runs `uv sync --frozen`. When local
source edits exist, scheduled updates print a notice and keep using the local code;
scanning still runs. Manual `monitor update` refuses a dirty checkout. No command
commits, pushes or discards source changes. The scan builds/verifies local SQLite;
production D1 and Pages are only updated through the existing publication workflow.

```bash
uv run python -m unittest discover -s tests -v
uv run modelsheet db build
uv run modelsheet db seed
uv run modelsheet db verify
```

The source changes for native monitoring must be reviewed and committed explicitly
before normal automatic fast-forward updates resume. Runtime configuration and
observations should be backed up independently of Git.
